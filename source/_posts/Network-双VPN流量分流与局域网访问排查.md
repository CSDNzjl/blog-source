在企业里同时挂两路 VPN（例如公司零信任客户端 + 某业务专用 Secure Connect），或单 VPN 开了强制隧道时，很常见的一类故障是：**目标 IP「明明该通」，却 ping 不通、tracert 走错口、浏览器一直转圈**。表象像应用问题，根因往往在操作系统的路由选择上。

本文从路由表机制讲起，说明为什么双 VPN 会「抢默认路由」，如何用最长前缀匹配做精准分流，以及同网段冲突、客户端清路由、DNS 劫持等容易踩坑的地方。以 Windows 为主，原理可迁移到其他系统。

> **适用读者**：实施、运维、需要在多网络环境里自助排障的开发。  
> **前置**：会看 `ipconfig` / `route print`，不要求会配企业 VPN 服务端。

## 1. 问题长什么样

典型场景往往叠在一起：

| 现象 | 常见误解 | 更接近真相的解释 |
|------|----------|------------------|
| 连上 VPN 后家里打印机、NAS 全挂 | 「VPN 把 Wi‑Fi 掐了」 | 默认路由被 VPN 接管，本地网段流量也被送进隧道 |
| 双 VPN 时，A 网通、B 网挂，或反过来 | 「某个客户端坏了」 | 两个默认路由只能有一个 Metric 胜出，另一路失去全局转发 |
| 某台内网服务器偶发可达 | 「服务器不稳定」 | 路由在重连后被 flush，或被同网段直连路由盖住 |
| 域名打不开，IP 有时能开 | 「DNS 服务器挂了」 | VPN 劫持了系统 DNS，解析结果与当前出口不一致 |

共同点：**流量没有走你以为的那条路**。浏览器、业务客户端只是受害者；决策发生在系统路由表（以及部分零信任客户端额外的策略层）。

## 2. 真正在打架的是默认路由

操作系统转发数据包时，先查路由表。VPN 客户端为了「接管上网」，通常会注入一条默认路由：

```text
网络目标        网络掩码          网关 / 下一跳        接口
0.0.0.0         0.0.0.0           <VPN 虚拟网关>      <VPN 虚拟网卡>
```

含义是：凡是没有更精确匹配的目的地址，一律交给这条路由。于是出现两类经典模式。

### 2.1 强制隧道（Full Tunnel）

所有流量进 VPN。好处是统一出口、便于审计；代价是本机局域网（`192.168.x.x`、`10.x` 家用段等）也可能被卷进隧道，表现为「连上公司网，家里设备全死」。

### 2.2 双 VPN：不是「都能通」，是「谁的 Metric 更小」

Windows 可以同时存在多条默认路由，但真正生效的是 **Metric（跃点数）更小** 的那条。另一条默认路由还在表里，却几乎抢不到全局流量。

结果是：

- 被选中的 VPN：像「总出口」；
- 落选的 VPN：若没有更具体的目的网段路由，发往其内网的包会误走另一条 VPN，或走回本地 Wi‑Fi。

所以双 VPN 环境下的「分流」，本质不是让两个默认路由和平共处，而是：**给必须走某条隧道的目标，补上更具体的静态路由**。

> 补充：不少企业客户端还会改接口 Metric、注入大量 `/24`、`/16` 网段路由，甚至在内核/驱动层做策略转发。系统路由只是你能直接干预的一层；若服务端策略不允许，本地改路由也救不了。

## 3. 解法：用更「具体」的路由压过默认路由

路由器选路遵循 **最长前缀匹配（Longest Prefix Match）**：掩码越长，匹配越精确，优先级越高。

| 路由类型 | 示例 | 前缀长度 | 优先级 |
|----------|------|----------|--------|
| 默认路由 | `0.0.0.0/0` | `/0` | 最低 |
| 网段路由 | `192.168.1.0/24` | `/24` | 中 |
| 主机路由 | `192.168.1.5/32` | `/32` | 最高 |

因此，给关键服务器加一条 `/32` 主机路由，指向目标 VPN 的虚拟网卡下一跳，就能在默认路由「抢走全世界」的情况下，把这几个 IP 精确拽回正确通道——这就是手工版的 **Split Tunneling（拆分隧道）**。

企业侧理想做法是：在 VPN 管理后台直接配置「仅下列网段走隧道」。客户端侧静态路由是后台管不到、或双 VPN 策略互相打架时的自救手段。

## 4. Windows 操作清单

以下假设：希望 `192.168.1.5`、`192.168.1.3`、`192.168.0.199` 走某路 VPN（示例虚拟网卡地址为 `10.10.10.81`）。请换成你环境里的真实值。

### 4.1 确认虚拟网卡与接口索引

管理员 CMD / PowerShell：

```bat
ipconfig
route print
```

关注两类信息：

1. **VPN 虚拟网卡的 IPv4**（如 `aTrustVNIC`、`VirtualNet`、Hillstone 虚拟适配器）——常作为下一跳；
2. **接口列表里的 Idx（接口索引）**——部分点对点 VPN 更适合用 `IF <Idx>` 指定出口，而不是填一个「看起来像网关」的地址。

若 `route add` 报错或加完不生效，可试：

```bat
route -p add 192.168.1.5 mask 255.255.255.255 0.0.0.0 IF <接口索引>
```

哪种写法有效，取决于该 VPN 适配器是「像以太网」还是「点对点隧道」。以你机器上 `route print` 里同类路由的既有写法为准，照葫芦画瓢最稳。

### 4.2 以管理员添加持久静态路由

普通权限会提示「请求的操作需要提升」。用 **管理员** 命令行：

```bat
route -p add 192.168.1.5 mask 255.255.255.255 10.10.10.81
route -p add 192.168.1.3 mask 255.255.255.255 10.10.10.81
route -p add 192.168.0.199 mask 255.255.255.255 10.10.10.81
```

- `-p`：写入持久路由，重启后仍在；
- 掩码 `255.255.255.255`：单主机，避免误伤整个网段；
- 下一跳：目标 VPN 虚拟网卡地址（或按上一节改用 `IF`）。

查看是否写入成功：

```bat
route print -4
```

在「活动路由」和「持久路由」两处都应能看到对应条目（持久路由在重连后是否仍被客户端保留，见第 6 节）。

### 4.3 可选：批处理一键恢复

部分零信任客户端重连时会 `route flush` 或重写路由表，`-p` 也不一定扛得住。可把命令存成 `fix-vpn-routes.bat`，连上 VPN 后以管理员运行一次：

```bat
@echo off
route -p add 192.168.1.5 mask 255.255.255.255 10.10.10.81
route -p add 192.168.1.3 mask 255.255.255.255 10.10.10.81
route -p add 192.168.0.199 mask 255.255.255.255 10.10.10.81
pause
```

注意：VPN 断开后虚拟网卡 IP 可能变化，脚本里的下一跳要跟着改，或改为基于接口索引的写法并在注释里写清「先 `route print` 确认 Idx」。

### 4.4 删路由

```bat
route delete 192.168.1.5
```

持久路由一并清掉时，确认 `route print` 的持久区不再残留，避免「删了活动路由、重启又冒出来」。

## 5. 验证：看第一跳，而不是只看能不能 ping

连通性测试容易误导：VPN 虚拟网卡常禁 ICMP，第一跳全是 `* * *` 并不等于失败。

```bat
tracert -d 192.168.1.5
```

| 结果 | 含义 |
|------|------|
| 第一跳之后很快出现内网网关 / 目标侧地址 | 大概率已进入正确隧道 |
| 第一跳直接是家里路由器（如 `192.168.0.1`） | 流量仍走本地默认出口，静态路由未生效或被覆盖 |
| 第一跳进了「另一条」VPN 的地址空间 | 双 VPN 抢路，下一跳指错或 Metric/接口选错 |

同时可对照：

```bat
pathping -n 192.168.1.5
powershell -Command "Find-NetRoute -RemoteIPAddress 192.168.1.5 | Format-List"
```

`Find-NetRoute` 能直接告诉你：系统此刻会选哪张网卡、哪个下一跳——比凭感觉猜出口清晰得多。

## 6. 异常场景：路由「加上了」仍不通

### 6.1 权限不足

报错含「提升 / elevated」：不是命令写错，是没管理员权限。

### 6.2 同网段冲突（最阴的一种）

目标是 `192.168.0.199`，本机 Wi‑Fi 也是 `192.168.0.0/24`。两边 IP 规划撞车时：

- 系统可能认为目标在「直连网段」，优先走本地 ARP，而不是你的 VPN 主机路由；
- 即便 `/32` 理论上更长，实践中仍可能因接口选路、弱主机模型、客户端策略等表现为「加了路由却 ARP 本地」。

应对思路：

1. 用 `Find-NetRoute` / `tracert` 确认实际出口网卡；
2. 显式指定 `IF <VPN 接口索引>`；
3. 长期方案是推动网段规划错开（业务内网不要和常见家用 `192.168.0.0/24`、`192.168.1.0/24` 重叠），或让 VPN 侧下发足够具体且带正确接口的路由。

### 6.3 安全策略拦截（路由通 ≠ 业务通）

aTrust、Hillstone 等零信任方案，除了改系统路由，还有应用层 / 驱动层访问控制。服务端未授权该资源时：

- 路由、tracert 可能「看起来进隧道了」；
- 业务端口仍被丢弃或重置。

这类问题本地路由解决不了，需要 IT 在控制台加资源 / 策略白名单。排查时把「三层是否可达」和「应用是否放行」分开看，避免在客户端空转。

### 6.4 重连后路由消失

原因通常是：

- 当时没加 `-p`；
- 客户端重连时重写路由表，持久路由被覆盖或下一跳网卡 IP 已变。

处理：脚本化恢复；或向管理员要官方的拆分隧道网段列表，减少手工维护。

### 6.5 DNS 与路由不一致

路由已指向内网，浏览器却访问域名失败：VPN 常会改系统 DNS 或做 DNS 劫持。表现是「IP 能开、域名不能」或「解析到了另一套环境的地址」。

权宜之计：

- 调试阶段直接用 IP；
- 需要域名时，用 `nslookup 域名 内网DNS` 对比系统默认解析；
- 必要时对指定 VPN 接口用 `netsh` 写入内网 DNS（改系统 DNS 有副作用，改完记得还原）。

### 6.6 不要忽略 IPv6

若目标同时有 AAAA 记录，而 IPv6 仍走另一条默认路由，会出现「偶发走错路」。可临时：

```bat
ping -4 目标
curl -4 http://...
```

确认问题是否只在 IPv4 路径上；长期应同样检查 IPv6 路由表（`route print -6`）。

## 7. 可复用的排查顺序

遇到「VPN 已连接但某内网 IP 不通」时，建议按层收敛，而不是一上来狂加路由：

```text
1. 目标是否应用层问题？
   → 换 IP 访问、换端口、看服务是否监听

2. 本机选路是否正确？
   → Find-NetRoute / tracert 看出口网卡与第一跳

3. 路由表里有没有更具体的冲突项？
   → route print，找同前缀、同网段、Metric 更优的条目

4. 静态路由能否纠正？
   → /32 + 正确下一跳或 IF；必要时 -p 或脚本

5. 是否被零信任策略挡住？
   → 路由已正确仍业务失败 → 找管理员加资源授权

6. DNS 是否和出口一致？
   → nslookup 对比；调试先用 IP
```

把「选路」和「授权」分开，能少走很多弯路。双 VPN 场景下，优先给 **少数关键主机** 加 `/32`，而不是一上来改默认路由 Metric——后者往往刚改完就被客户端改回去。

---

## 8. 小结

- 双 VPN / 强制隧道下的「访问异常」，多数是 **默认路由与 Metric 竞争**，不是应用随机抽风。
- 静态主机路由利用 **最长前缀匹配**，用 `/32` 压过 `/0`，是客户端侧最可控的分流手段。
- 验证看 **实际出口与第一跳**，不要被 ICMP 屏蔽误导。
- 同网段重叠、客户端清路由、零信任策略、DNS 劫持，是「route add 成功却仍不通」的四大常见原因。
- 能推动服务端配置拆分隧道、错开网段规划时，优先走正规配置；本地静态路由适合作为精确、可回滚的补丁。

路由表是网络世界的「交通规则」。VPN 只是往规则库里塞了几行字——读懂这些字，比换客户端、重装系统要快得多。
