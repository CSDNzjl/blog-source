学习内容：
本月我系统梳理了虹光项目计划模块的完整业务闭环：ERP 销售订单进入 plan_sales_order 后，经发布生成 plan_production_master_plan；再通过工艺同步将 plan_product / plan_product_route 复制到主计划子表 plan_process_route；排产计算各工序起止时间与下发量后进入「待下发」；计划下发生成制芯/造型/组装三类 plan_daily_plan，派工后产生 plan_report_process 与报工记录 plan_report_record，并与质量检验、NCR 评审、仓储入库形成联动。三类日计划在业务上虽共用一张表，但状态机、领料规则、报工类型（CORE / ORDER / ASSEMBLY）各不相同，这是我本月理解业务时投入精力最多的部分。
我深入学习并实现了两套排产逻辑。「按产能」以自然日箱数 CN 为上限，结合 Q1/Q2/Q3（砂芯/毛坯/成品）、废品率 R（来自 plan_release_rule）、ceil 进位及跨主计划产能池 plan_process_capacity_daily_usage 做逐日分摊；「按工时」则依赖工厂日历 plan_factory_calendar 与班次 plan_working_shift，按 H = Q × GS 在真实班次内累加工时，并处理 max(确认时刻 A, 班次开始 B)、休息时段、已排任务占用等边界。此外还掌握了熔炼/浇注工序与造型共用时间窗、V0525 产品当毛坯时 Q2/Q3 特例等规则，并把这些内容沉淀进《生产主计划计划排产规则说明》。
计划模块作为编排中枢，需要调用质量（过程检验任务推送、NCR 不合格评审）、仓储（库存查询、领料出库、末道合格入库）、工装（模具台账与释模）、工艺（vcs_hongguang_core_param / assembly_param / cast_param 等 JSON 参数）等多个服务。我学习了如何通过独立 Client 封装远程调用、如何用 sourceRef 区分派工推送与报工后推送、以及质量模块回调同一 submitProcessWorkReport 入口实现「手工报工」与「检验同步报工」逻辑复用，避免在计划侧维护两套报工分支。
我掌握了派工后首道 reportable_quantity 的赋值差异：制芯日计划派工即可报工（首道 = 计划数量），造型/组装首道初始为 0，须完成砂芯领料或毛坯领料后通过 calcKBQ 增加可报工量。领料数据分别来自 sand_usage_json（造型砂芯）、product_bom.roughCastings（组装毛坯）、工装模具台账（不影响可报工）；出库库别、批次号校验及 picked_materials / picked_moulds JSON 持久化结构也在本月实现与文档化。

二、感悟及需求等：
感悟：
1. 计划模块是制造执行的业务中枢，而非简单 CRUD
月初我从建表、做页面入手，月中逐步卷入排产算法、领料门闸、质量回写、仓储入库，越发体会到计划模块处在工艺、仓储、质量、工装多条线的交汇点。一个报工动作背后可能同时触发 NCR 推送、下道工序可报工量变更、末道入库、日计划完工释模等多条副作用。把端到端数据流画成状态图并写入文档后，自己和协作同事沟通效率明显提升，也减少了很多「这个状态能不能点」的反复确认。
2.状态机与副作用边界必须文档化，否则维护成本指数上升
本月我处理过多个易混淆场景：主计划「待下发」工艺同步须完整排产撤销，而「已下发」计划撤回却不回滚工厂日历占用；制芯派工即可报工但造型/组装须领料；V0525 特例下不生成组装日计划但造型末道按产成品入库。这些规则如果只靠代码记忆，新人很难接手。我通过《计划模块逻辑说明》附录的状态枚举速查表和撤销/撤回差异说明，把隐性业务知识显性化，这也是我个人从「写功能」向「建体系」转变的一次实践。
需求：
V0525 特例下，按产能排产落库的 Q2 与计划下发预览建议量在部分场景可能不一致（预览公式简化、排产走完整 SC 分支）。建议产品确认以排产落库为准还是以预览展示为准，并在前端提示差异原因，避免计划员困惑。
同一 product_code 下已支持多 process_type、多 product_version 并存，销售订单发布自动匹配「批量 + 最大版本」，手工同步可弹窗选择。但试制转批量、工艺升版后旧版本是否停用、停用记录是否参与自动匹配（当前不过滤 status）等问题，仍需与工艺模块、产品同事共同制定规则，避免现场选错版本导致路线与实物不一致。
三、工作过程中发现的问题及解决建议：
1.雪花 ID 精度与 SQL 异常（5/22 已修复）
联调过程中出现过雪花 ID 在 JSON/JavaScript 边界精度丢失及 SQL 异常未友好提示的问题。我已在 scheduling 模块补充类型转换与异常处理。建议项目层面统一 Long 型主键序列化策略（前端转字符串、Feign DTO 注解），并在关键写接口增加业务异常包装，避免现场只看到 500 而无定位信息。
2.物料分组树形结构 ID 传递错误（5/29 已修复）
物料分组管理优化时，树组件父子节点 ID 传递不一致导致勾选、保存异常。我修复了树形构建与 ID 映射逻辑。建议对全项目树形选择组件封装统一约定（nodeKey、parentId 字段名），减少各模块各自实现带来的重复 bug。
3.工艺同步与排产撤销耦合复杂，误操作风险高
「待下发」主计划执行工艺同步会先撤销排产（删除产能占用、清空路线时间、日历占用重算），操作正确但用户感知不强。我已在文档中明确差异，建议前端在确认弹窗中增加简要说明（如「将清除已排产时间与产能占用」），必要时提供只读预览受影响数据条数。
